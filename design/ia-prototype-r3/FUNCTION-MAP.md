# 蒲公英任务流程重设计 · 原型评审 R2

2026-10-15。分支 `design/toast-2-task-flow-prototype`。基线为 Windows 当前 `0.1.95` 工作树，HEAD `0342968d19600f0507ac2434d6f763056aac1319`，含原有大量暂存、未暂存与新增文件。上一方案 `ui/toast-2-workbench-redesign` 仅作为回退参考，不视为已完成重构。本轮不继续改业务 renderer。

## 评审对象与打开方式

解压后双击 `index.html`，无需服务、安装或联网。默认从“达人复核”开始，可按左侧导航走完整流程；`review.html` 集中展示前后对照。原型只保存 `pgy-ia-prototype-r2` 下的虚构状态；右上角时钟图标可以重置。没有 desktopAPI、真实账号、业务文件或云端连接；普通 CSV 下载也全部为虚构数据。

这次评审的是任务组织、入口、操作顺序和状态衔接。原型使用原生 HTML/CSS/JS，独立于现有 Electron 入口，未接业务。原业务仍沿用已有技术栈，后续接入以评审通过为前提。项目分组只是上层视图概念，不搬迁现有 runs、不复制账号配置、不迁移 Cookie、不重写稳定身份。

## 任务导向的信息架构

```text
合作项目（保留进度与上下文）
├─ 项目概览：继续上次任务 / 本批结果 / 待处理问题
├─ 发现与候选：蒲公英人工搜索 / 已有表 / 链接 → 初筛 → 确认采集范围
├─ 采集任务：启动前检查 → 串行队列 → 安全暂停/停止 → 结果/故障恢复
├─ 达人复核：选择结果批次 → 列表比较 → 详情与来源 → 选入建联
├─ 建联交付：固定本次名单 → 通道与话术 → 未发送准备 → 普通导出或飞书交接
├─ 历史与分析：搜索草稿 / 执行记录 / 结果证据 / 导出历史 / AI分析
└─ 设置与维护：角色账号 / 校准 / 模板 / 飞书连接与经纪人 / 精确测试维护 / 录制回放
```

新导航比旧的三段日常流程多两项，这是有意取舍：采集是长任务，建联是有外发风险的独立决策；让它们拥有稳定页面，减少“同一页上不知道哪一个操作正在生效”的问题。概览给出继续上次任务的入口，不强制从登录页重走。真实登录仍须在使用对应账号前核验。

### 列表与详情

- 表格用于比较昵称、方向、粉丝、报价、联系方式与跟进状态；窄屏允许表格区域横向滚动，页面整体不溢出。
- 点击一行打开/更新右侧预览。上一位/下一位保留列表上下文；概览、跟进与来源分开。
- 候选阶段点击行编辑初筛；资料复核阶段点击行预览，编辑通过明确按钮进入。
- “选择行”只产生批量作用范围；“选入建联”改变业务选择。两个概念在界面和状态里分开。
- 结果批次在列表前明确显示。新任务完成可只看本次已保存对象；切回旧批结果保留原状态，旧执行准备失效。

### 批量动作与进度

批量栏只在当前筛选中有已选对象时出现；显示作用人数，排除/移除另作确认。候选移除与结果删除分开。采集启动用单独检查对话框绑定数量、登录、规则和范围；默认不采排除对象，“全部候选”需另确认。原型用手动推进，不模拟成真实高速采集。

请求暂停、暂停生效、撤销待暂停、请求跳过、生效跳过、请求停止与已停止分开；跳过不是已保存。风险停止不自动导航、不自动开始下一项；登录失效和本地保存失败各给对应恢复动作。采集完成由人点击去复核，不自动跳进补采或邀约。

### 建联交付与异常恢复

- 固定本次名单，逐人预览话术；通道、名单、身份或内容变化撤销旧准备/审批。异步准备按计划对象、版本、索引和当前人绑定，旧回调不能标记新对象已准备。
- PGY 采用同一批次“仅准备，不发送 → 不发送，准备下一位 → 不发送，完成本批准备”；准备人数与发送人数分别显示，原勾选和待建联不变。
- 邮件只提供有效邮箱交接，缺邮箱明确反馈；打开邮箱不触发补采、不自动填写收件人、不写信、不发送。微信通道提供普通交接表，执行文件与普通工作簿分开。
- 飞书操作先选方式和明确经纪人，再看字段差异，最后模拟确认/回读。正式补录只核对目标与将写字段；正式记录不能进入测试清理。结果不明时仅核对，不自动重试。
- 原型最终发送按钮始终不可用，也不生成可执行小蜜蜂文件。

## 五分钟建议评审路线

1. 打开原型，默认复核页。点击达人行→侧栏“下一位”→编辑备注；勾两行，再“选入建联”。观察行选择和业务勾选的区别。
2. 去发现与候选。切换三种来源，点击行编辑初筛；模拟人工登录，输入“第35-50位”查看独立检查点。创建采集任务时比较默认、优先、最近与全部范围。
3. 采集任务推进一位→请求暂停→到达安全点→继续；选择下一位遇到风控→推进。确认结果保留且不能自动继续。重置后可走正常完成，再打开对应结果批次。
4. 从复核生成两人建联方案。仅准备第一位→不发送下一位→不发送完成。确认发送0，原勾选保留。改话术检查旧准备消失。
5. 飞书交接先不选经纪人试预览，再明确选择→字段差异→模拟确认；演示结果不明。到设置中尝试将正式记录进入测试清理，确认被阻断。

## 设计取舍与接入前的明确缺口

- 不采用全局看板拖拽作为主要操作：移动列容易把“已准备”误读为“已发送”。状态转换使用明确按钮与当前对象确认。
- 不让网页长期占半屏；代价是从复核打开主页多一个显式动作。发现模式仍并排展示网页，角色页本身不销毁。
- 项目组织不等于跨run自动合并。原型用8位虚构样本展示，不证明真实大规模性能或多批合并正确性。
- 低频工具保留可找到的去向，未在原型重做解析器、AI、Excel引擎、录制器或凭证管理。B/C条目不能标记已完成功能交付。
- 原型未验证原生BrowserView隐藏/显示/焦点/缩放，也未打包、安装或验真实账号；这些是评审通过后的单独接入与验收阶段。
- UI覆盖路由与对话框入退场、焦点返回、当前行/导航状态变化、列表选择/筛选、异步准备与进度变化；支持减弱运动。实际业务长列表、中文输入法与原生网页交叉焦点仍待接入验收。

本轮验收只针对原型交互。检查记录见 `evidence/acceptance.json` 与 `evidence/coverage.json`；不重复跑全套业务测试，也不借旧方案49条命令宣称新结构已接入。

## 面包评审重点

请优先判断三个结构选择：**全宽名单+侧栏是否适合连续复核、采集任务是否值得独立导航、名单确认后再进入建联交付是否清晰**。这些方向确认前，不继续接入业务或调整旧版本配色。

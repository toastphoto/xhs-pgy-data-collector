未关闭项

1. **P2 / F2：监管器未成功创建时，窗口退出会陷入无法完成的重试。**

   定位：`desktop-app/main.js:2840`、`desktop-app/main.js:2853`、`desktop-app/main.js:2946`、`desktop-app/main.js:8548`。

   触发：fork 无法创建监管器，ChildProcess 发出 error、close，但没有 exit。生产代码只在 exit 清 backendProc；保留的对象已经没有 PID、IPC 断开，stopBackend 每次返回失败，before-quit 又因 backendProc 存在而阻止退出。

   本轮将真实 Node fork 接入精确生产函数，用不存在的测试 execPath 确定性触发 ENOENT。实际观察到 error→close、未分配 PID、无 exit；生产函数仍保留引用，窗口事件替身观察到退出被阻止并显示错误提示。没有启动任何业务后端或真实 Electron 窗口。这个事件模式也符合 Node 对启动失败的说明：不能依赖每次 error 后都会有 exit。[Node 官方 ChildProcess 文档](https://r2.nodejs.org/docs/latest-v24.x/api/child_process.html#event-error)

   影响：在资源/权限等导致监管器无法启动时，用户可能既无法启动服务，也无法通过正常退出完成收尾。未主张本次安装版发生过该条件。

   建议：区分“从未创建成功且已 close”和“仍拥有活动子进程”。对前者在同一引用/启动代次下清理无效句柄、token，允许退出；对后者继续保留所有权。补 error→close 无 exit 的回归，不能简单把任意 error 都当作子树已退出。

2. **P2 / F2：taskkill 自身不返回时，主进程超时后重试仍被监管器永久挡住。**

   定位：`desktop-app/lib/qa_backend_supervisor.js:8`、`:14`、`:17`；主进程超时见 `desktop-app/main.js:2942`。

   触发：监管器已启动本次 taskkill，但该清理命令既不 error 也不 exit，`killing=true` 一直不复位。主进程的8秒定时器只结束本轮等待，没有让监管器中的清理尝试超时或收尾。

   生产 stopBackend 与真实监管器 factory 接线的故障注入结果：两次停止请求、两次主进程超时、20次监管轮询，taskkill 尝试数始终为1；所有权保留，但再次退出没有发起可恢复的清理。Windows taskkill 使用替身，不把此结果写成实机曾挂起。

   建议：为本次清理 helper 建立有界超时、完成/失败状态及尝试代次。超时后安全处理并确认本次 helper 的状态，保留业务子树所有权，再允许明确重试；不能仅无条件把 killing 置 false 后并发启动无限 taskkill。补“监管器已收到 stop、其 taskkill 不返回”的回归。

3. **P2 / F1：旧 ChildProcess 的 error 回调仍可覆盖新实例状态。**

   定位：`desktop-app/main.js:2840`，开发态类似路径见 `desktop-app/main.js:2893`。

   原探测 Promise 与 exit 已有引用/代次防护，但 error 回调仍无条件发布 running=false。故障注入：旧实例退出→新实例就绪→对旧对象投递 error，新实例仍被正确拥有，却多收到一条 OLD_ERROR/不运行状态。

   影响：违反本轮“旧异步结果不能覆盖新实例”的防护要求。该精确迟到事件顺序本轮由替身注入，尚未在 Windows 自然复现；不将它描述为已发生的现场故障。

   建议：error 回调也核对当前引用与启动代次；启动失败的清理同时按第1项区分是否真正创建过进程，避免用只接受健康进程的 ownsBackend 直接丢弃必要的启动失败报告。补旧 error 事件不改新实例状态的断言。
